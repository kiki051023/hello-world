## 🎯 一、总体判断

两份文档合计提出约 20 个改进项，但**不是 20 个独立任务**。整合后发现 3 个联动关系和 1 个根因：

| 联动/根因 | 说明 | 处理方式 |
|---|---|---|
| 🔗 **UE-3（前端 CRUD 封装）≡ Phase 12（后端代码生成器）** | 生成器产出配置式页面 = 自动落地 CRUD 封装，同一件事两端 | **合并为一个任务**，避免前端先写封装、生成器再推翻 |
| 🔗 **Phase 11 字典 = 前端硬编码文案的根因** | 状态/类型文案前后端双重硬编码（ScoreAudit 的 `{DRAFT:'草稿'...}`、每页 rules），没有字典，前端规范化无从谈起 | 字典先行，前端规范文案后置依赖 |
| 🔗 **Phase 10 调度 = 业务自动化的前置** | 预警扫描/学期切换/通知清理都挂在它下面 | 独立底座，最先做 |
| ⚠️ **README 已失真** | README 还是"6 表 7 Controller"，实际 37 实体 25 Controller | 与任何功能开发无关，但影响项目对外形象，零成本修复 |

**结论：20 个改进项 → 4 个里程碑 + 1 个根因修复，约 3~4 周单人工作量，可并行两条流。**

## 🚀 三、四里程碑执行计划

### 里程碑 1：安全底座 + 移动可用（约 1 周）→ 最优先

| 任务 | 来源 | 工作量 | 说明 |
|---|---|---|---|
| M1-1 定时任务框架（预警扫描/学期切换/通知清理/任务超时回收） | Phase 10.1 | 2~3d | `@EnableScheduling` + 任务配置/日志表（phase10 迁移） |
| M1-2 接口限流（登录/验证码/导入/成绩批量） | Phase 10.2 | 1~2d | `@RateLimit` 注解 + Redis 计数器，429 友好提示 |
| M1-3 在线用户管理（列表/强退） | Phase 10.3 | 1d | Redis `online:*` + 黑名单强退 |
| M1-4 响应式 + 侧栏折叠 | UE-1 | 1d | `collapse` 持久化 + <768px 抽屉 + 筛选区换行 + 表格横向滚动 |
| M1-5 README 刷新 | — | 0.5d | 37 实体/25 Controller/9 大模块全量清单 |

**验收**：4 个定时任务上线且日志可见；连发 6 次登录触发 429；375px 宽浏览器全功能可用；README 不再失真。
**为什么最优先**：调度/限流是安全与自动化底座（0 依赖其他任务）；响应式是唯一致命体验缺陷且独立；README 零成本。组合拳一周见效。

### 里程碑 2：字典 + 生成器（效率杠杆，约 1 周）→ 中期最值

| 任务 | 来源 | 工作量 | 说明 |
|---|---|---|---|
| M2-1 数据字典（2 表 + 管理界面 + `@Dict` 注解翻译） | Phase 11.1 | 2d | 首批：性别/学历/奖惩/请假/资助/预警/就业状态 |
| M2-2 缓存体系（班级下拉/组织树/字典/看板统计 `@Cacheable`） | Phase 11.2 | 1~2d | 变更 `@CacheEvict`；命中率 DEBUG 日志 |
| M2-3 CRUD 生成器 + CrudPage 封装（**合并做**） | Phase 12 + UE-3 | 3~4d | 配置驱动页面：`columns + form + api` 三份配置即可一页 |
| M2-4 前端规范文案迁移（依赖 M2-1） | UE-3 配套 | 1d | ScoreAudit/审批面板等硬编码状态映射改字典 |

**验收**：5 个 CRUD 页改为配置式且行为不变（每页 ≥300 → ≤100 行）；生成器产出 1 个全新模块（如宿舍管理）可直接编译运行；全库无 `{DRAFT:'草稿'}` 式硬编码映射。
**为什么中期**：字典是文案根因、缓存是性能、生成器是长期效率——三者互锁，一次做完收益最大。生成器必须与 CrudPage 一起设计，否则返工。

### 里程碑 3：业务增值（约 1 周）→ 面向学生价值

| 任务 | 来源 | 工作量 | 说明 |
|---|---|---|---|
| M3-1 消息多渠道（邮件 + 企微 Webhook；Channel 抽象 + 失败重试） | Phase 13.1 | 2d | 短信**明确不做**（成本敏感） |
| M3-2 学生自助门户（课表/成绩趋势/审批进度/预警/实习状态五卡片） | Phase 13.2 | 2~3d | 复用现有 API + 2~3 个聚合接口 |
| M3-3 空状态统一 + 全局搜索（依赖字典） | UE-4 | 1~1.5d | `el-empty` + Ctrl+K 命令面板 |

**验收**：审批通过同时发邮件、失败有重试日志；学生账号可见五卡片且与教师端数据一致；全站无裸空表格。
**为什么第三**：业务价值高但依赖字典（M3-3）与既有 API，排在底座和效率杠杆之后。

### 里程碑 4：体验 + 工程收尾（约 1 周，可后置）

| 任务 | 来源 | 工作量 | 说明 |
|---|---|---|---|
| M4-1 暗色主题贯通 | UE-2 | 1d | `.dark` token 分支 + header 切换按钮，登录页与主界面同源 |

## ⚖️ 四、优先级决策依据（为什么这个顺序）

| 决策 | 依据 |
|---|---|
| 底座 > 效率 > 业务 > 体验 | 依赖关系驱动：调度/限流无下游依赖；生成器依赖字典；学生门户依赖既有 API；标签页/暗色纯体验可后置 |
| 安全任务（限流/在线强退）排第一周 | 登录/验证码/导入当前无限流，是唯一"会出事"的敞口（安全 > 体验，防数据丢失原则） |
| 生成器与 CrudPage 合并 | 分开做 = 前端封装一次 + 生成器推翻一次，重复建设 |
| 短信/i18n/TS/虚拟滚动明确拒绝 | 成本敏感 + 单院校中文内网 + 数据量小，收益 < 成本（与用户偏好一致） |
| Flowable/多租户/微服务拒绝 | 过度设计：现有状态机审批够用，单院校部署无多租户需求（YAGNI） |
